그누가 "AWS 는 서비스 이름부터 외우기 전에, 누가 뭘 할 수 있는지부터 잡고 싶다"고 해서 1편은 계정과 IAM 으로 정리해 봤어요. 내용은 2026-11-23 에 공식 문서로 확인한 범위예요.

## 왜 IAM 부터인가

AWS 에서는 서버를 켜는 것도, 파일을 읽는 것도 전부 API 요청이에요. 그리고 모든 요청은 "누가(주체), 무엇을(액션), 어디에(리소스)" 하려는지 검사를 받아요. 이 검사를 맡는 서비스가 IAM 이에요. 여기가 헐거우면 뒤에 쌓는 네트워크와 암호화가 다 소용없어요.

## 계정이라는 경계

AWS 계정은 리소스와 청구서, 권한이 담기는 가장 바깥 상자예요. A 계정의 주체는 B 계정 리소스에 기본적으로 접근하지 못해요. 그래서 운영과 개발을 계정으로 나누면 사고가 번지는 범위가 줄어요.

계정이 여러 개면 AWS Organizations 로 묶어요. 조직을 만든 계정이 관리 계정, 나머지가 멤버 계정이고, 멤버 계정은 OU(조직 단위)라는 폴더로 정리해요.

## 루트 사용자: MFA 걸고 서랍에 넣기

계정을 만들 때 쓴 이메일로 로그인하는 주체가 루트 사용자예요. 계정당 1개이고, 단독 계정과 관리 계정의 루트는 정책으로 줄일 수 없어요. 다만 조직의 멤버 계정 루트는 SCP 로 제한돼요([SCP 문서](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_scps.html)).

- **MFA 필수**: 단독, 관리, 멤버 계정 모두 루트는 MFA 가 필요해요. 콘솔 첫 로그인 시도 후 14일 안에 등록해야 해요. 종류는 패스키/보안 키, 인증 앱(TOTP), 하드웨어 TOTP 이고 문서는 피싱에 강한 패스키나 보안 키를 권해요. ([루트 MFA 문서](https://docs.aws.amazon.com/IAM/latest/UserGuide/enable-mfa-for-root.html))
- **사용 최소화**: 루트는 루트만 할 수 있는 일에만 써요. 단독 계정이라면 계정 이메일과 비밀번호 변경, 계정 폐쇄, 그리고 S3 MFA Delete 설정 같은 것들이에요(Organizations 를 쓰면 관리 계정이 멤버 계정의 폐쇄와 이메일 변경을 할 수 있어요). ([루트 사용자 문서](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_root-user.html))
- **루트 접근 중앙 관리**: Organizations 를 쓰면 멤버 계정의 루트 자격 증명(비밀번호, 액세스 키, 서명 인증서, MFA)을 중앙에서 지울 수 있어요. 조직에서 새로 만든 계정은 처음부터 루트 자격 증명이 없어요. 잘못 잠근 S3 버킷 정책 삭제 같은 일부 작업은 관리 계정이나 위임 관리자가 짧은 권한 세션으로 대신해요.

## 사용자, 그룹, 역할, 정책

| 이름 | 한 줄 정의 | 자격 증명 |
|---|---|---|
| IAM 사용자 | 계정 안에 만든 사람 또는 프로그램 1명 | 장기(비밀번호, 액세스 키) |
| IAM 그룹 | 사용자 묶음. 정책을 한 번에 붙이는 용도 | 없음(로그인 불가) |
| IAM 역할 | 누군가 잠깐 맡는 권한 묶음 | 임시(STS 발급) |
| 정책 | 허용과 거부를 적은 JSON 문서 | 해당 없음 |

한도도 감을 잡아 둘게요. 계정당 IAM 사용자 5,000, 역할 1,000(조정 가능), 사용자 1명이 속할 수 있는 그룹 10개, 사용자당 액세스 키 2개예요. 한도는 바뀌니 [IAM 쿼터 문서](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_iam-quotas.html)에서 확인하세요.

**사람은 IAM Identity Center 로.** [IAM 모범 사례](https://docs.aws.amazon.com/IAM/latest/UserGuide/best-practices.html)는 사람에게 IAM 사용자를 하나씩 만들어 주는 대신 ID 공급자와 연동해 임시 자격 증명을 쓰게 하고, 중앙 접근 관리는 IAM Identity Center 로 하라고 권해요. 워크로드는 IAM 역할을 쓰고, 장기 액세스 키는 역할을 못 쓰는 경우에만 남겨요.

## 정책 JSON 읽는 법

example-app 의 로그 버킷을 사무실 IP 에서만 읽게 하는 정책이에요.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::example-app-logs/*",
    "Condition": {
      "IpAddress": { "aws:SourceIp": "203.0.113.0/24" }
    }
  }]
}
```

- **Effect**: Allow 인가 Deny 인가
- **Action**: 어떤 API 인가. `서비스:동작` 형태예요.
- **Resource**: 대상의 ARN. `/*` 는 버킷 안의 모든 객체예요.
- **Condition**: 언제만 적용되나. 여기서는 출발 IP 가 203.0.113.0/24 일 때만이에요.

읽는 순서는 "Effect 를 Action 에 대해 Resource 에, 단 Condition 일 때"예요. 버킷 정책 같은 리소스 기반 정책에는 누구에게 적용할지 적는 Principal 이 하나 더 붙어요.

## 정책 평가 로직: 순서보다 원리

정책은 여러 종류가 겹쳐요. 순서를 줄줄 외우기보다 원리 네 가지를 잡는 게 안전해요.

1. **기본은 암묵적 Deny**: 아무도 허용하지 않은 요청은 거부돼요.
2. **명시적 Deny 는 항상 이김**: 어느 정책에든 Deny 가 하나 있으면 다른 Allow 가 몇 개든 거부예요.
3. **상한은 권한을 주지 않음**: SCP, RCP, 권한 경계는 "여기까지만"이라는 울타리예요. 울타리 안이라도 ID 기반이나 리소스 기반 정책의 Allow 가 따로 있어야 해요. ID 기반 정책과 권한 경계는 **교집합**이에요.
4. **같은 계정 안에서 ID 기반과 리소스 기반은 합집합**: 둘 중 하나가 허용하면 돼요.

![명시적 Deny, 조직 상한, 리소스 기반 정책, ID 기반 정책, 권한 경계와 세션 정책 순으로 확인하는 결정 트리](img/aws-01-account-iam-2.png)

그림은 [공식 평가 로직 문서](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_evaluation-logic_policy-eval-denyallow.html)의 순서를 줄인 거예요. 문서에서 리소스 기반과 ID 기반 Allow 가 권한 경계와 세션 정책보다 앞에 나온다는 점만 알아 두세요. 역할 신뢰 정책과 KMS 키 정책은 예외로 명시적 Allow 가 꼭 필요하고, 다른 계정 사이의 접근은 규칙이 더 있어요.

**RCP 는 비교적 새 요소예요.** SCP 가 "우리 조직의 주체가 할 수 있는 일"의 상한이라면, RCP(리소스 제어 정책)는 "우리 조직의 리소스에 할 수 있는 일"의 상한이에요. 모범 사례 문서는 둘을 함께 쓰라고 권하고, 둘 다 권한을 부여하지는 않아요. 2024-11-13 발표 때는 5개 서비스(S3, STS, KMS, SQS, Secrets Manager)였고 목록은 계속 바뀌니 [RCP 사용 설명서](https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_rcps.html)에서 확인하세요([발표 글](https://aws.amazon.com/about-aws/whats-new/2024/11/resource-control-policies-restrict-access-aws-resources/)).

## 역할과 STS: 왜 장기 키보다 안전한가

액세스 키는 지우기 전까지 계속 유효해요. 코드나 노트북에 남은 키가 새면 누군가 알아챌 때까지 쓰여요.

역할은 달라요. 역할을 맡으면(AssumeRole) STS 가 **만료 시간이 붙은 임시 자격 증명**을 내줘요. 역할 세션은 기본 1시간이고 역할 설정으로 최대 12시간까지 늘릴 수 있어요. 좋은 점은 세 가지예요.

- 새어 나가도 만료되면 쓸모가 없어요.
- 코드나 설정 파일에 키를 저장할 필요가 없어요. EC2 같은 워크로드는 역할을 붙이면 자격 증명을 자동으로 받고 갈아 줘요.
- 누가 이 역할을 맡을 수 있는지를 신뢰 정책으로 따로 통제해요.

## 시험에서는 이렇게 나와요

- "EC2 의 앱이 S3 에 접근해야 한다. 가장 안전한 방법은?" 정답은 거의 항상 **IAM 역할**이에요. 액세스 키를 코드나 인스턴스에 넣는 보기는 오답이에요.
- "Allow 가 있는데 왜 거부되나?" 어딘가의 명시적 Deny 또는 SCP 같은 상한을 찾는 문제예요.
- "SCP 에 Allow 를 넣었는데 권한이 안 생긴다" 상한은 권한을 주지 않는다는 점을 묻는 거예요.
- "여러 계정의 직원 로그인을 한곳에서" 는 IAM Identity Center 예요.

## 요약

- 계정이 가장 바깥 경계, 여러 계정은 Organizations 로 묶어요.
- 루트는 MFA 를 걸고 루트 전용 작업에만 써요.
- 사람은 Identity Center, 워크로드는 역할. 장기 키는 최후의 수단이에요.
- 기본은 Deny, 명시적 Deny 가 최우선, SCP/RCP/권한 경계는 상한일 뿐이에요.

## 확인 문제

**1.** EC2 인스턴스에서 도는 애플리케이션이 S3 버킷을 읽어야 해요. 가장 안전한 방법은?
① IAM 사용자의 액세스 키를 코드에 넣는다 ② 액세스 키를 인스턴스의 환경 변수에 넣는다 ③ 필요한 권한만 가진 IAM 역할을 인스턴스에 연결한다 ④ 루트 사용자의 액세스 키를 쓴다

**2.** 어떤 IAM 사용자의 ID 기반 정책은 s3:* 를 Allow 하고, 같은 계정의 버킷 정책은 그 사용자의 s3:DeleteObject 를 명시적으로 Deny 해요. 객체 삭제 요청의 결과는?
① 허용. ID 기반 정책이 우선이다 ② 거부. 명시적 Deny 가 항상 이긴다 ③ 허용. 합집합이다 ④ 나중에 만든 정책을 따른다

**3.** 조직의 SCP 가 ec2:* 를 Allow 해요. 멤버 계정의 한 IAM 사용자에게는 아무 정책도 붙어 있지 않아요. 이 사용자가 EC2 인스턴스를 시작하면?
① 허용. SCP 가 권한을 줬다 ② 거부. SCP 는 상한일 뿐 권한을 주지 않는다 ③ 허용. 멤버 계정은 SCP 를 상속한다 ④ 관리 계정에서만 허용된다

**4.** 루트 사용자에 대한 설명으로 맞는 것은?
① 일상 관리 작업에 쓰는 것이 권장된다 ② 멤버 계정의 루트는 MFA 가 필요 없다 ③ MFA 를 걸고 루트 전용 작업에만 쓴다 ④ 액세스 키를 만들어 팀이 함께 쓴다

**5.** 한 회사가 AWS 계정 여러 개를 쓰고, 직원이 사내 ID 로 한 번 로그인해 각 계정에 접근하게 하려 해요. AWS 가 권장하는 방법은?
① 계정마다 직원별 IAM 사용자를 만든다 ② IAM Identity Center 를 ID 공급자와 연동한다 ③ 루트 사용자를 공유한다 ④ 액세스 키를 계정마다 발급해 나눠 준다

## 정답과 해설

1. **③** 역할을 연결하면 STS 임시 자격 증명을 자동으로 받고 갱신해요. 장기 키를 저장하는 ①②④는 유출되면 지울 때까지 유효해요.
2. **②** 어느 정책에든 명시적 Deny 가 있으면 다른 Allow 와 상관없이 거부예요. 합집합은 Deny 가 없을 때의 이야기예요.
3. **②** SCP 는 권한을 부여하지 않아요. ID 기반이나 리소스 기반 정책의 Allow 가 없으니 암묵적 Deny 예요.
4. **③** 모든 계정 유형의 루트에 MFA 가 필요하고, 일상 작업은 Identity Center 의 관리자 계정으로 해요.
5. **②** 모범 사례는 사람에게 ID 공급자 연동과 임시 자격 증명을, 중앙 접근 관리에는 IAM Identity Center 를 권해요.
