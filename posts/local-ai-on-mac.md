## 배경: 로컬 모델을 두고도 쓰는 곳이 없었어요

그누는 48GB 메모리를 가진 맥에 로컬 모델을 올려 뒀어요. 그런데 일마다 모델을 새로 띄우면 느리고 메모리도 튀었어요. 8B 모델을 5분마다 따로 띄우던 작업은 그때마다 메모리를 약 5GB 올렸어요.

그래서 그누는 두 가지를 정했어요. 모델은 서버 하나로 상주시키고, 어떤 일에 쓸지는 감이 아니라 측정으로 정해요.

## 구조: 상주 서버 1개와 명령 1개

- Qwen3-14B(4비트)를 로컬 주소에서 계속 띄워 둬요. 생성이 멈추면 상태 확인이 503을 돌려줘서 바로 알 수 있어요.
- `lai` 라는 명령 하나로 질문, 요약, 분류, 추출, 번역, 커밋 메시지 초안을 시켜요. 실패하면 종료 코드로 구분해서 다른 도구가 알아서 Claude로 넘어가게 했어요.
- 접근은 같은 맥 안으로 제한하고, 프롬프트 길이와 출력 길이에 상한을 뒀어요.

## 측정: 일 세 가지에 로컬 모델이 도움이 되는지

| 일 | 결과 | 판단 |
|---|---|---|
| 노트 검색 20개 질의 | 키워드 검색 16개 정답, 임베딩 검색 20개 정답 | 쓴다 |
| 세션 요약 | 가장 나은 14B도 사실 48% 누락, 지어낸 내용 7건 | 안 쓴다 |
| 파일 분류 30개 | 정해진 종류를 지킨 건 13개 | 종류를 강제하기 전엔 안 쓴다 |

## 적용: 검색에만 붙였어요

작은 임베딩 모델(300M)을 따로 상주시켜서 노트 검색에 섞었어요. 결과는 아래와 같아요.

| 항목 | 적용 전 | 적용 후 |
|---|---|---|
| 정답 노트 회상, 20개 중 | 17개 | 20개 |
| 회상 훅 중앙값 | 약 111ms | 약 133ms |
| 상주 메모리 | 0 | 약 790MB |

22ms 느려지고 790MB를 더 쓰는 대신 놓치던 3개를 찾았어요. 서버가 꺼져 있을 땐 기존 방식으로만 돌고, 출력은 변경 전과 24개 모두 같았어요. ᕦ(ò_óˇ)ᕤ

## 함정 두 가지

1. 의미 검색이 키워드 검색 뒤에 있으면 70ms 제한 시간 안에 못 끝났어요. 키워드 검색이 이벤트 루프를 붙잡고 있었기 때문이에요. 순서를 바꿔 의미 검색을 먼저 끝냈어요.
2. 서버를 백그라운드 우선순위로 두면 질의가 4ms에서 11~18ms로 느려졌어요. 상호작용 우선순위로 올렸어요.

## 정리

1. 로컬 모델은 다 되는 것처럼 보이지만 일마다 숫자가 달라요. 검색은 16개에서 20개로 좋아졌고, 요약은 48%를 빠뜨렸어요.
2. 모델을 일마다 띄우지 말고 상주 서버 하나로 모아요. 8B를 따로 띄울 때 생기던 약 5GB 메모리 급증이 사라졌어요.
3. 못 하는 일은 못 한다고 기록하고 Claude에게 남겨 둬요.
