## 배경: 폰 채팅의 연결 방식을 웹소켓으로 구현했어요

그누네 팀은 폰에서 에이전트와 대화하는 앱의 연결을 맥으로 직접 이어지는 웹소켓으로 만들고 있었어요. 프로토콜 문서, 서버, 클라이언트까지 구현했고, 서버 보안 리뷰도 한 차례 받았어요.

## 문제: 쓰는 사람에게 서버 준비를 시키는 구조였어요

이 방식은 다른 사람이 쓰려면 서버와 주소를 갖춰야 했어요. 도구를 쓰려고 인프라를 준비시키는 구조는 제품으로 맞지 않았어요. 완성도가 높아질수록 이 문제가 더 선명해졌어요.

## 선택: 만든 걸 버리고 중계 구조로

중계를 사이에 두는 설계가 같은 문제를 더 단순하게 풀었어요. 맥이 먼저 중계로 나가 연결하고 폰도 같은 중계에 붙어요. 그래서 그누네 팀은 웹소켓 구현을 배포하지 않고 보류했어요.

| 항목 | 수치 |
|---|---|
| 웹소켓 구현 커밋 | 12개 |
| 서버 테스트 | 16개 |
| 클라이언트 테스트 | 15개 |
| 배포된 것 | 0개 |

만든 코드와 테스트 31개는 참고 자료로 남기고 쓰지 않아요. ( ˘ω˘ )

## 같이 정한 것들

- 동영상은 허용하되 20MB까지는 한 번에, 그보다 크면 4MB 조각으로 나눠 최대 100MB까지 보내요. 영상은 받은 폴더에만 저장하고 30일 뒤 정리해요.
- 앱 업데이트 파일은 서버가 직접 내려주지 않고 채팅 카드 안에서 암호화해 전달해요. 받은 파일의 해시를 서명된 목록과 대조한 뒤에만 설치 화면을 띄워요.

## 정리

1. 구현이 많이 진행됐어도 구조가 문제면 접는 게 맞아요. 이미 쓴 시간은 판단 기준이 아니에요.
2. 접어도 문서와 테스트는 남겨요. 다음 설계가 어디서 막혔는지 알려 줘요.
3. 새 경로를 열 때는 "봉투 밖에 무엇이 실리는가"를 먼저 따져요.
