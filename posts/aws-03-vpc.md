그누가 "보안 그룹은 매일 만지는데, VPC 를 처음부터 그리라고 하면 손이 멈춘다"고 해서 3편은 VPC 설계로 정리해 봤어요. 네트워크 연재 2편(서브넷 계산)과 3편(라우팅, 최장 일치)을 그대로 이어받는 글이에요. 숫자는 2026-11-23 에 공식 문서에서 확인한 값이에요. 한도와 가격은 바뀌니 링크에서 확인해 주세요.

## 왜 VPC 가 필요한가

AWS 는 수많은 고객이 같은 설비를 나눠 써요. 그 안에서 "여기는 내 네트워크"라고 논리적으로 떼어 낸 공간이 VPC(Virtual Private Cloud)예요. IP 대역, 서브넷, 라우팅, 방화벽 규칙을 내가 정해요. VPC 는 리전 하나에 속하고, 서브넷은 **가용 영역(AZ) 하나에만** 속해요. 그래서 AZ 장애에 버티려면 같은 역할의 서브넷을 AZ 마다 만들어야 해요.

## CIDR 과 예약 IP 5개

VPC 를 만들 때 맨 먼저 정하는 것이 IPv4 CIDR 이에요. 서브넷의 CIDR 은 **/16(가장 큼)부터 /28(가장 작음)** 까지 쓸 수 있어요([서브넷 크기 문서](https://docs.aws.amazon.com/vpc/latest/userguide/subnet-sizing.html)). VPC 자체의 허용 범위는 같은 사용 설명서에서 확인해 주세요.

2편에서는 사용 가능한 호스트를 "2^호스트 비트 - 2"로 셌죠. AWS 는 서브넷마다 **처음 4개와 마지막 1개, 모두 5개**를 예약해요. 10.0.0.0/24 라면 .0(네트워크 주소), .1(VPC 라우터), .2(DNS), .3(향후 사용), .255(브로드캐스트 주소)예요. 그래서 식이 "2^호스트 비트 - 5"로 바뀌어요.

- /28: 호스트 비트 4개, 2^4 = 16, 16 - 5 = **11개**
- /24: 2^8 = 256, 256 - 5 = **251개**

일반 네트워크 문제라면 /28 의 답이 14지만 AWS 문제에서는 11이에요.

## 퍼블릭과 프라이빗은 라우트 테이블이 정한다

서브넷을 만들 때 "퍼블릭" 체크박스가 있는 게 아니에요. 정의는 하나예요. **서브넷에 연결된 라우트 테이블에 인터넷 게이트웨이(IGW)로 가는 경로가 있으면 퍼블릭, 없으면 프라이빗**이에요. 서브넷은 라우트 테이블 하나에만 연결되고, 여러 서브넷이 한 테이블을 같이 쓸 수 있어요.

퍼블릭 서브넷의 라우트 테이블은 보통 두 줄이에요. "10.0.0.0/16 → local"과 "0.0.0.0/0 → IGW"예요. 네트워크 3편의 최장 일치가 그대로 적용돼요. 목적지가 10.0.20.5 면 두 줄 모두 맞지만 /16 이 더 길어서 local 로 가고, 8.8.8.8 은 0.0.0.0/0 만 맞으니 IGW 로 나가요. 경로만으로는 부족하고, 인스턴스에 공용 IP 도 있어야 인터넷과 통신해요.

## IGW 와 NAT Gateway

**인터넷 게이트웨이(IGW)** 는 VPC 와 인터넷을 잇는 문이에요. **NAT Gateway** 는 프라이빗 서브넷의 서버가 바깥으로 **나가기만** 하게 해 줘요(패치 내려받기 같은 용도). 바깥에서 먼저 시작한 연결은 받지 않아요.

기본형인 퍼블릭 NAT Gateway 는 **퍼블릭 서브넷에 두고 탄력적 IP(EIP)를 붙여요**([NAT 문서](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-nat-gateway.html)). 서브넷에 두니 AZ 하나에 묶여요(zonal). 그 AZ 가 죽으면 그 NAT 를 쓰던 다른 AZ 의 서버도 못 나가니, AZ 마다 하나씩 두고 프라이빗 라우트 테이블도 AZ 별로 나눠요.

2025-11-19 에 **Regional NAT Gateway** 가 나왔어요([What's New](https://aws.amazon.com/about-aws/whats-new/2025/11/aws-nat-gateway-regional-availability/), [문서](https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateways-regional.html)). 공식 문서에서 확인한 것만 적을게요.

- NAT Gateway ID 하나가 워크로드가 있는 AZ 로 자동 확장, 축소해요.
- 퍼블릭 서브넷이 필요 없고, 자체 라우트 테이블이 자동으로 생겨요.
- AZ 당 IP 는 최대 32개(zonal 은 8개), 새 AZ 로 확장하는 데는 최대 60분이 걸려요.
- 프라이빗 NAT 는 지원하지 않아요. GovCloud 와 중국을 뺀 상용 리전에서 써요.

## 보안 그룹 vs NACL

| 구분 | 보안 그룹(SG) | 네트워크 ACL(NACL) |
|---|---|---|
| 적용 단위 | 인스턴스(네트워크 인터페이스) | 서브넷 |
| 상태 | stateful: 응답은 자동 허용 | stateless: 응답도 규칙 필요 |
| 규칙 종류 | 허용만 | 허용과 거부 |
| 평가 방식 | 모든 규칙을 보고 하나라도 허용이면 통과 | 번호(1~32766)가 낮은 것부터, 맞으면 거기서 끝 |
| 기본 규칙 수 | 60개(인/아웃 각각) | 20개(인/아웃 각각) |

출처: [보안 그룹과 네트워크 ACL 비교](https://docs.aws.amazon.com/vpc/latest/userguide/infrastructure-security.html#VPC_Security_Comparison), [보안 그룹](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-security-groups.html), [네트워크 ACL](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-network-acls.html)

![요청과 응답이 NACL 과 보안 그룹을 지나는 순서. 보안 그룹은 응답을 자동 통과시키고 NACL 은 아웃바운드 규칙이 필요함](img/aws-03-vpc-2.png)

NACL 은 443 인바운드만 열면 응답이 못 나가요. 응답은 클라이언트의 임시 포트(그림에서는 50000)로 가니 아웃바운드에 그 범위를 열어야 해요. 그리고 "특정 IP 를 막아라"는 거부 규칙이 없는 SG 로는 못 해요. NACL 에 낮은 번호로 거부를 넣는 게 답이에요 ^^7

## VPC 엔드포인트와 공용 IPv4 요금

**VPC 엔드포인트**는 인터넷을 거치지 않고 AWS 서비스에 닿는 통로예요. Gateway 엔드포인트는 S3 와 DynamoDB 용이고, Interface 엔드포인트는 PrivateLink 기반으로 서브넷마다 네트워크 인터페이스가 생겨요([개념 문서](https://docs.aws.amazon.com/vpc/latest/privatelink/concepts.html)).

**공용 IPv4 주소**는 쓰는 중이든 놀리든 **시간당 $0.005** 예요([VPC 가격 페이지](https://aws.amazon.com/vpc/pricing/), 2026-11-23 확인). 30일이면 0.005 x 24 x 30 = 개당 $3.6 이에요. NAT Gateway 요금은 리전마다 달라서 숫자를 적지 않을게요. 같은 가격 페이지에서 리전을 골라 확인해 주세요.

## 예시: example-app 3티어 설계

가상의 서비스 example-app 을 AZ 2개에 올려 볼게요. VPC 는 10.0.0.0/16 이고 /24 로 잘라요. /16 안에 /24 는 2^(24-16) = 256개가 들어가니 6개를 써도 250개가 남아요. 서브넷마다 쓸 수 있는 IP 는 251개예요.

| 서브넷 | AZ | CIDR | 기본 경로(0.0.0.0/0) |
|---|---|---|---|
| 퍼블릭 A | A | 10.0.0.0/24 | IGW |
| 퍼블릭 B | B | 10.0.1.0/24 | IGW |
| 프라이빗 A | A | 10.0.10.0/24 | NAT GW A |
| 프라이빗 B | B | 10.0.11.0/24 | NAT GW B |
| DB A | A | 10.0.20.0/24 | 없음 |
| DB B | B | 10.0.21.0/24 | 없음 |

![example-app 의 VPC 구성도. AZ 2개에 퍼블릭, 프라이빗, DB 서브넷이 하나씩 있고 라우트 테이블이 서브넷 성격을 정함](img/aws-03-vpc-1.png)

보안 그룹은 계층을 따라 사슬처럼 걸어요. 로드밸런서 SG 는 인터넷에서 443 을, 앱 SG 는 **로드밸런서 SG 에서 오는 것만**, DB SG 는 **앱 SG 에서 오는 것만** 허용해요. 출발지에 IP 대역 대신 보안 그룹을 적는 거예요.

한도도 알아 두세요. 기본값은 **리전당 VPC 5개**, VPC 당 서브넷 200개, AZ 당 NAT Gateway 5개이고 모두 증가 요청으로 조정할 수 있어요([VPC 쿼터 문서](https://docs.aws.amazon.com/vpc/latest/userguide/amazon-vpc-limits.html), 2026-11-23 확인).

## 시험에서는 이렇게 나와요

- SAA-C03 도메인1: "프라이빗 서버가 패치를 받아야 한다"(NAT Gateway), "특정 IP 차단"(NACL), "DB 는 앱 서버만 접근"(SG 가 SG 를 참조), "S3 에 인터넷 없이 접근"(Gateway 엔드포인트)
- ANS: CIDR 설계와 예약 IP 계산, 라우트 테이블의 최장 일치, stateful 과 stateless 의 패킷 흐름

## 요약

- 서브넷은 AZ 하나에 속하고 IP 5개가 예약돼요. /28 은 16 - 5 = 11개예요.
- 퍼블릭 서브넷은 "라우트 테이블에 IGW 경로가 있는 서브넷"이에요.
- NAT Gateway 는 나가는 전용이에요. zonal 은 AZ 마다 두고, regional 은 하나가 AZ 로 자동 확장해요.
- SG 는 stateful 에 허용만, NACL 은 stateless 에 허용과 거부, 번호 순서예요.

## 확인 문제

**1.** AWS 에서 10.0.5.0/28 서브넷에 실제로 쓸 수 있는 IP 주소는 몇 개일까요?
① 16 ② 14 ③ 11 ④ 8

**2.** 어떤 서브넷이 "퍼블릭 서브넷"이 되는 조건은?
① 이름에 public 을 넣는다 ② 라우트 테이블에 IGW 로 가는 경로가 있다 ③ 라우트 테이블에 NAT Gateway 로 가는 경로가 있다 ④ 보안 그룹이 0.0.0.0/0 을 허용한다

**3.** NACL 은 인바운드 443 만 허용하고 아웃바운드는 모두 거부해요. 보안 그룹은 인바운드 443 을 허용해요. 외부에서 오는 HTTPS 접속은?
① 정상 동작한다 ② 요청이 서버에 닿지 못한다 ③ 요청은 닿지만 응답이 NACL 아웃바운드에서 막힌다 ④ 응답이 보안 그룹 아웃바운드에서 막힌다

**4.** 공격 IP 198.51.100.7 한 개만 차단하려고 해요. 알맞은 방법은?
① 보안 그룹에 거부 규칙 추가 ② NACL 에 허용 규칙보다 낮은 번호로 거부 규칙 추가 ③ NACL 에 허용 규칙보다 높은 번호로 거부 규칙 추가 ④ 라우트 테이블에서 IGW 경로 삭제

**5.** 퍼블릭(zonal) NAT Gateway 에 대한 설명으로 맞는 것은?
① 프라이빗 서브넷에 두고 EIP 없이 쓴다 ② 퍼블릭 서브넷에 두고 EIP 를 붙인다 ③ 인터넷에서 먼저 시작한 연결을 프라이빗 서버로 전달한다 ④ VPC 에 하나만 만들 수 있다

## 정답과 해설

1. **③** 2^4 = 16개에서 AWS 예약 5개를 빼면 11이에요. 14는 일반 네트워크 계산의 답이에요.
2. **②** 퍼블릭과 프라이빗은 라우트 테이블의 IGW 경로 유무로 갈려요. NAT Gateway 를 가리키면 프라이빗 서브넷이에요.
3. **③** NACL 은 stateless 라서 응답도 아웃바운드 규칙이 있어야 해요. 보안 그룹은 stateful 이라 응답을 자동으로 허용해요.
4. **②** 보안 그룹에는 거부 규칙이 없어요. NACL 은 낮은 번호부터 보고 맞으면 끝나니, 거부가 허용보다 앞 번호여야 해요.
5. **②** 퍼블릭 서브넷에 두고 EIP 가 필요해요. 나가는 연결 전용이고, 기본 한도는 AZ 당 5개예요.
